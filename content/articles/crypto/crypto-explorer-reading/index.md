发送端说已经完成，对方却说没有收到。你拿到一串 TxID，打开网页，又看到 From、To、Value、Fee。到底哪一行能说明钱去了哪里？

这一课只做查账。浏览公开交易记录不需要连接钱包，也不需要签名。下面用普通 Ethereum 交易和 ERC-20 代币转移解释字段；所有金额示例都是虚构，不提供可直接使用的转账地址。

## 一、从发送记录进入正确的浏览器

先回到本人发送平台或钱包，打开这一笔记录，确认币种、网络、时间与交易哈希。平台内部订单号未必是链上哈希；内部划转也可能根本没有链上交易。

如果记录提供“在区块浏览器查看”，检查打开的域名和网络。也可以从所用网络的官方资料找到浏览器，再复制哈希查询。以 Ethereum 主网为例，可使用 [Etherscan](https://etherscan.io/)；其他网络应使用对应入口，不能只因都以 0x 开头就混查。

在浏览器搜索框粘贴完整哈希，进入交易详情。搜不到时，先查是否选错网络、复制了订单号、发送端仍在审核或该浏览器尚未同步，再联系发送端核对。**查无结果，不足以证明资金已经丢失。** [Etherscan 查询说明](https://info.etherscan.com/viewing-transactions-on-etherscan/?id=50)

页面上的广告、评论和陌生链接不是处理工单。查询过程中若有人要求连接钱包“修复到账”或付钱“同步余额”，先停止，回到自己核实的官方支持入口。

## 二、读交易页，先找六个关键位置

字段位置会变，名称也可能有差异。先找这六组信息，不必从第一天就读懂所有技术参数。

| 常见字段 | 在核对什么 | 不能单独证明什么 |
| --- | --- | --- |
| Transaction Hash，交易哈希 | 是否为本次发送记录对应的交易 | 一串真实哈希不证明它与自己的付款有关 |
| Status，状态 | 等待、执行成功或失败 | 成功不代表目标平台已经记账 |
| Block / Timestamp | 是否进块、在哪个时间处理 | 固定几分钟不等于所有平台的到账要求 |
| From / To 或 Interacted With | 谁发起，直接交互对象是什么 | To 若为合约，不一定是最终收款人 |
| Token Transfers | 哪种代币从哪里转到哪里、数量多少 | 同名代币不一定是目标资产 |
| Value / Transaction Fee | 原生币附带金额与实际网络费 | 不能把 Value 当成所有代币的转账总值 |

Ethereum 的交易文档把 value 定义为交易附带的 ETH 数量，也区分直接向账户发送与调用合约。浏览器把这些信息整理成可读页面。[Ethereum 交易字段](https://ethereum.org/developers/docs/transactions/)

“成功”首先说明这笔链上交易按执行结果完成。它不是对项目、收款人或交易商业目的的认证。只有把状态和资产变化放在一起，才知道它是否完成了你想做的事。

## 三、Value 是零，为什么仍能收到代币

看一张经过简化的**虚构记录**。A、B、C 只是教学代号，不是可收款地址。

| 字段 | 示例内容 |
| --- | --- |
| 网络 | Ethereum 主网 |
| Status | Success |
| From | 地址 A |
| Interacted With (To) | 代币合约 C |
| Value | 0 ETH |
| ERC-20 Tokens Transferred | 合约 C 的代币：A → B，25 个 |
| Transaction Fee | 0.001 ETH |

这笔交易调用合约 C 处理代币转移，没有在 value 字段附带 ETH。因此 **0 ETH 不等于没有转移资产**；本题的代币记录写着 B 收到 25 个。

核对实际收款时，不能把 C 复制出来当作下次收款地址。C 是本次交互的代币合约，B 才是这条代币转移记录里的接收方。看清哪个字段表达哪种角色。

还缺一个条件：C 是否确实是你要收的那种代币合约。陌生合约同样可以显示熟悉的名称和图标。应按正确网络核对发行方与接收平台认可的合约身份；复杂兑换、批量转账也可能有多条记录，不能只读第一行。

这个例子限定为标准的简单代币转移。对不熟悉的合约，仅凭一条自称“转账”的日志或浏览器标签，不足以替代对合约、余额变化及业务结果的核验。

## 四、Gas 花了多少，失败为什么也可能收费

先分清 Gas Limit 与 Gas Used。前者是允许使用的上限，后者是实际消耗；成交后的费用核对还需要实际每单位 Gas 价格，而不是把上限直接当成账单。

用普通 Ethereum 交易做一道算术题：假设 Gas Used 为 50,000，实际 Gas 价格为 20 Gwei。1 Gwei＝0.000000001 ETH，所以费用为：

**50,000 × 20 × 0.000000001＝0.001 ETH。**

不要再把 0.001 ETH 从代币数量里扣一遍。本例发送 25 个代币，与支付 0.001 ETH，是两种资产的变动。若是交易所提币，还应把平台收取的提币费与链上实际 Gas 分开，不能假定平台向你收的费用等于这一条链上账单。

链上执行失败也可能收费，因为执行过程已消耗计算资源。例如执行时用尽 Gas，状态变更会回退，但已消耗的 Gas 不会因此全部返还。只在发送前被钱包拒绝、根本没有广播的情况，与已经上链后失败不同。[Ethereum Gas 机制](https://ethereum.org/developers/docs/gas/)

L2 可能还有额外的数据等费用项目，智能账户和代付方案也可能改变付款关系。本文公式用于明确限定的普通 Ethereum 例子，其他场景应核对该网络的费用明细。

## 五、链上成功以后，平台为什么还没记账

假设代币已经在正确网络、按正确合约转到了目标平台控制的充值地址，仍有几个平台侧问题要检查：

- 这是不是该账户当前提供的充值资料，必要的 Memo 或 Tag 是否正确？
- 平台是否支持该代币版本，净收到数量是否达到最低额？
- 所需确认或最终性条件是否满足，充值是否暂停或需要进一步审核？
- 平台充值历史有没有对应记录，状态和提示是什么？

区块浏览器只能帮助你核对链上发生的部分。它不知道平台内部应该给哪个用户增加余额，也不能替银行确认法币入账。发送平台处理、链上执行、接收平台记账要分开看。

确认数也不能只看“大不大”。按接收端对该网络与资产的要求核对，不能将另一条链的数字照搬。查清楚之前，不要再追加一笔希望“冲开”前一笔。

## 六、三条记录，练习找出还缺什么证据

**记录 A：**对方发来的哈希是真的，状态成功，数量 50，但接收地址与自己的充值地址不一致。

还不能认为这就是付给你的款。应核对正确目标与原订单；一笔成功交易只能证明它自己的执行记录，不能替另一笔付款作证明。

**记录 B：**详情 Value 为 0 ETH，正确代币合约的转移记录写着自己的地址收到 25，状态成功。

不应因 Value 为零认定没收到代币。继续核对网络、完整地址、数量与余额；若接收方是平台，再看充值记账条件。

**记录 C：**状态失败，扣了 ETH 网络费，没有本次预期的代币转移结果。

不能根据扣费就认定代币已付给对方。分别核对执行错误、实际资产变化与网络费用，先查原因，不重复提交同一请求。

## 七、把查到的内容整理成一份排查记录

遇到问题时，可以在自己的记录里填写下面这些字段。它们让官方支持能定位交易，也能减少来回猜测。

| 字段 | 填什么 |
| --- | --- |
| 发送端与时间 | 平台或钱包名称、时间与时区 |
| 平台订单号 | 与链上哈希分开记录，没有则注明不适用 |
| 网络与交易哈希 | 本次实际发送的网络及完整哈希 |
| 资产身份 | 币种与必要的合约信息 |
| 预期与实际 | 预期接收地址、数量，对照链上记录 |
| 接收端状态 | 支持条件、最低额、充值历史与错误原文 |

公开讨论时不要附带证件、银行账户或地址与真实身份的完整关联。哈希本身通常是公开信息，但公开它可能同时暴露自己的交易关联；向核实过的支持渠道提供所需资料即可，任何时候都不附上私钥、助记词或验证码。

能把上述字段解释清楚，就已经从“看一个绿色成功”进到了“核对谁在什么网络收到了什么”。接下来再看自管钱包，你会更容易区分链上记录与钱包显示。
