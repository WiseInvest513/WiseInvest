# Wise 文章默认生成流程

适用：MyBlog 新文章、操作教程、产品比较、原理解释、补绑说明、研究与系列内容。用户只需说明主题；AI 默认执行这里的流程，不需要用户重复提示导读、版式、封面和邀请卡。

## 两层约束

1. `wise-article-authoring`、`wise-article-layout`、`wise-article-referrals` 等 skills 决定如何理解材料、按文章类型写作和复核。
2. 项目脚本控制草稿阶段与发布完整性。`prepare` 缺少逐篇导读就失败；`compose` 必须有与当前计划一致的准备记录；`finalize` 必须通过严格校验与当前内容的审阅检查。`npm run build` 还会先校验已发表内容，防止绕过草稿流程后漏填导读。

这里没有新增运行时 AI 接口，不会在读者打开文章时重新生成内容。不同文章保留同一种页面布局，但各自的读者、收获、准备和边界由 AI 依据本篇材料撰写。确定性的校验不能判断所有语义是否真实，也不能证明图片右上角确实放了正确品牌，所以仍需要生成 AI 看正文、看图、核对来源，不能只填“检查通过”。

## 第一步：先计划、导读，后正文

阅读已有文章、用户材料及必要的一手来源，决定文章类型：

| 类型 | 需要回答的实际问题 |
| --- | --- |
| `tutorial` | 产品是什么，哪些人能用，怎么操作，如何核对结果 |
| `referral` | 当前账户属于哪种状态，走什么处理路径，操作前有什么不可逆风险 |
| `comparison` | 比较维度与适用人群是什么，权利、费用和限制如何不同 |
| `concept` | 读者混淆了什么，通过机制、例子或计算能理解什么 |
| `research` | 证据支持什么判断，哪些反例与不确定性仍存在 |
| `journal` | 当时的时间背景和判断是什么，不能当作哪些实时建议 |
| `overview` | 这套内容或产品解决什么问题，应从哪个入口继续 |

不按类别分发模板句，不硬凑相同章节数；比较文不要求开户材料，理论文章不强塞交易入口。导读先明确本篇范围，写完正文后再核对它是否兑现。

计划 JSON 字段如下（各文案必须为当前文章单独生成）：

```json
{
  "id": "etf-fee-reading-example",
  "title": "ETF 交易费用怎么看：费率与最低佣金的区别",
  "categoryId": "index",
  "type": "concept",
  "summary": "从订单金额和最低收费理解费用计算，再核对自己的交割单。",
  "date": "2026-11-06",
  "access": "MEMBER",
  "target": "index/费用阅读示例/fee-guide.md",
  "guide": {
    "audience": ["对交易费率与单笔最低佣金容易混淆的 ETF 用户", "想读懂交割单，核对小额订单实际成本的人"],
    "outcomes": ["区分按成交额计算的费用与单笔收费下限", "从交割单核对买卖两侧费用，不只比较宣传费率"],
    "prepare": "准备自己的费率说明或交割单即可；这是一篇费用原理文章，不需要先开户或转入资金。",
    "status": "计算案例用于解释收费机制，不代表某家券商的现行报价，也不能替代本人账户的实际收费记录。"
  },
  "outline": ["为什么宣传费率与实际扣费不同", "怎样计算一笔订单的费用", "怎样对照交割单检查"],
  "readTime": 6
}
```

该例只说明格式，不能原样作为另一篇文章的导读。`subcategoryId`、`seriesId` 按需填写；`readTime` 省略时按正文估算。日期是文章日期，不是“所有规则已核验”的证明。`access` 是计划中的访问级别，需与项目实际静态权限一致；写入 frontmatter 不会自动修改权限。

```sh
npm run article:draft -- prepare --plan /absolute/path/plan.json
npm run article:draft -- compose --id ARTICLE_ID --body /absolute/path/body.md
```

计划与阶段记录保存在 `.article-drafts/ARTICLE_ID/`。缺少导读、计划被修改或未准备就调用 compose 时，命令会拒绝继续。AI 应修正计划并重新 prepare，而不是关闭校验。

## 第二步：正文与网站配置

正文使用已有共享阅读组件。compose 仅执行有明确含义的格式整理：换行统一、去掉与标题完全相同的顶部重复 H1、给正文 H2 连续中文编号；代码块不改写。它不会删除教程截图、替换邀请链接、擅改福利数字或为缺失事实补句子。

- 导读写入四个 frontmatter 字段：`guideAudience`、`guideOutcomes`、`guidePrepare`、`guideStatus`。前两项使用 ` | ` 分隔，不能包含管道分隔符作为正文字符。
- 邀请信息使用现有 `ArticleRegistrationCard` 解析格式和品牌配置。只有普通提及或补绑说明时不强塞新注册卡。新品牌先补真实图标与明确映射；保留用户确认的权益与条件，不能编造。
- 封面集中配置于 `lib/article-covers.ts`，网页文件放 `public/images/articles/covers/`。新图按约 640×360 WebP、尽量 10–20 KB、上限 25 KB 处理；复用真实平台标志与右上角原始 Wise 签名。原稿保存在 `assets/source-images/article-covers/`。两篇既有 BIT 原图例外不代表新文章可以跳过小图要求。
- 纯列表封面不放进正文。不要按“第一张图”或文件名猜测并删除操作图。
- 代码权限由 `lib/content-access.ts` 结合静态配置和文件内限时开放规则解析；默认 MEMBER，公开或 VIP 使用对应配置，不改其他文章权限。脚本复用真实解析结果，不只相信某个配置行的 access 字面值；数据库权限仍可能覆盖它，涉及上线权限需实际核验。
- 若指定系列，更新 `lib/article-library.ts` 中真实章节、阶段或综合教程映射，`lib/article-series.ts` 提供查询辅助。不要拿一篇文章重复充当多个可读章节，不生成指向未发布章节的可点击链接。
- 使用稳定 ID，不改别人的文章 ID 和路径。目标已存在时 finalize 会拒绝覆盖；已有文章改稿应在原文件小范围修改，再跑校验，而不是删掉重建。

```sh
npm run article:draft -- check --id ARTICLE_ID
```

缺少封面、错误图片路径、无效导读或不合格的结构等必须修好再继续。代码的通过只代表自动检查项通过，不替代内容审阅。

## 第三步：审阅当前成稿，再落入正式目录

AI 逐条核对并记录：导读是否与正文对应；事实与时效依据；封面与签名、正文图片；邀请卡和链接；静态权限与可选系列。`check` 返回当前计划、稿件与封面 SHA256，审阅记录必须使用这三个值：

```json
{
  "planSha256": "CHECK返回的当前计划哈希",
  "articleSha256": "CHECK返回的当前文章哈希",
  "coverSha256": "CHECK返回的当前封面哈希",
  "checks": {
    "guide": "写明导读中的收获分别由正文哪些内容提供，读者条件是否合适。",
    "facts": "列明所核对的一手材料、用户确认依据、分析时点及未确定事项。",
    "visuals": "记录实际看图结果，包括完整右上角签名、清晰度、品牌和正文截图用途。",
    "referrals": "核对实际邀请码、链接、福利及条件；没有邀请内容时说明不适用原因。",
    "access": "说明实际静态权限和系列配置与计划一致；不要冒称已检查线上数据库。"
  }
}
```

以上是写法说明，不是可以复制粘贴的审阅结论。必须填写实际检查结果，不能用 `true`、`OK`、套话或自动生成的“全部通过”。存在关键未决事实时保留草稿，不伪造审阅通过。计划、正文或封面修改后，旧哈希失效，应重新看改动后的成稿并记录。哈希凭据只锁定这三份材料，不锁定整个网站：若审阅期间更改品牌福利、系列或权限等共享配置，AI 仍需针对相关展示重新核对；finalize 会重新执行配置一致性检查，但不判断福利事实是否正确。

```sh
npm run article:draft -- finalize --id ARTICLE_ID --review /absolute/path/review.json
npm run article:validate
```

finalize 再次校验后才创建 `content/articles/` 下的正式文章，并保留审阅记录；**它只写本地，不提交 Git、不推送、不部署**。本地开发服务可能立即展示这篇正式文章，因此未完成内容不要提前写进该目录。

## 本站教程与路线引用卡片（2026-11-06 确认）

新增或改稿时，正文中引用本站文章、教程或系列路线，统一用卡片完整展示，不只挑部分产品处理。把句子里的入口整理为自然引导文字和独立卡片；同一处有多个教程时，连续写卡片行，复用响应式分组。**表格内的链接保留文字形式**，不塞卡片、不为卡片拆掉表格。外部来源、当前文章的章节锚点也保留文字链接；用户明确指定文字展示时按指定执行。

```markdown
[支付宝买入实操](/articles/index/mSIqvwVp){card}
[港资券商开户与入金](/articles/series/hk-stock-funding#stage-brokers){card}
```

统一复用 `ArticleLinkCard`、`ArticleLinkCardGroup` 和 `renderMarkdown`。文章卡片读取公开标题、摘要、阅读时长和独立列表封面；路线卡读取真实系列封面、简介和可读文章数。保留原链接的 query/hash，整张可点击，不复制目标正文、不影响访问权限、不新增正文目录标题。缺少元信息时运行时会退回文字链接，但交付前必须检查并修正缺失或坏链接，不能把静默降级当成已完成。邀请注册链接仍使用 `ArticleRegistrationCard`。

卡片左侧封面垂直居中、保持完整比例；右上角用绿色标签区分“学习文章”和“系列教程”。这是内容类型标记，不是筛选按钮，桌面、手机及深色模式共用同一规则。

交付前枚举本次文章的所有本站引用，分别核对正文卡片和表内文字链接，确认同组产品、段首入口、收尾推荐、系列路线均无遗漏。检查桌面、手机及深色模式的封面、跳转和分组；运行 `tests/article-link-card.test.mjs` 及相关预览测试。此规则用于今后的新增/改稿，历史全库迁移仍按用户指定范围进行。

## 构建门禁与旧稿兼容

`npm run build` 的 `prebuild` 首先执行 `npm run article:validate`，失败时不会继续生成图片索引或生产构建。Vercel 当前使用同一个 `npm run build` 命令。编辑中的草稿不在发表目录，故不会拖垮正常预览；有 ID 的正式文章不能靠缺字段或损坏 frontmatter 隐身绕过检查。

全库模式阻止必需字段、导读缺项/重复/已知套话及基础资源问题；旧稿非关键格式遗留可以警告处理。新稿 check / finalize 使用严格模式，并写入 `authoringVersion: 1`，入库后的构建也持续严格校验。代码不能控制 AI 的内部思考过程或阻止人手直接改文件，但能阻止不合格内容沿正常生成、构建流程继续流转。

共享组件变更继续运行对应的排版、邀请卡、图片和权限测试；不为了让门禁通过而改掉既有测试保护、静默隐藏导读、把所有权限改成公开或删掉真实截图。skills 与这份流程需随脚本接口同步维护。
